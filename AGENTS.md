# Small Nukem — AGENTS.md

**Read this first. It is everything a coding agent (Claude Code, Gemini,
Antigravity, Muse, any LLM) needs to continue this project cold.**
No other brief overrides it. Where it conflicts with an older brief,
spec draft, or in-file comment, this file + `docs/DECISIONS.md` win.

Small Nukem is a single-player, 2D, side-view browser game about starting
up and operating a real BWRX-300 small modular reactor — cold shutdown to
300 MWe on the grid — built on Samira D'Souza's BWRX-300 plant model.
Player character: Fluke Nukem. Guide: the Chief, in a brass CRT TV window.
Failures end in safe shutdown, never an explosion. Audience 15–30;
no childish framing, no multiplayer, no 3D.

**Current published build: ship #24 — `game/small-nukem.html` on `main`, 1,082,451 B,
MD5 `6dc80315b5ef9fb69d537227c3411ab0`. (Branch `claude/festive-pasteur-l8clmg` carries the unpublished ship #25 build, `fad27ff3…` — see §10.)** Live at
https://nuke.absolutejoker.ca (playtests use this URL only, never a
local address, and verify the loaded build is not a stale cached copy).

## 3. Game-file anatomy

One self-contained HTML file (~1 MB, 3 `<script>` blocks — the script
checker must report exactly that, all clean). Mobile portrait is the
primary platform (reference 390×844); desktop and gamepad are secondary.

Systems, in the order a reader meets them (full anchors, line tables,
and call sites in `docs/WIRING-MANIFEST.md` — use it, don't re-derive):

- **Physics — the `BWR` block.** Samira's model, embedded verbatim:
  `const BWR = (() => { … })();`. Fixed-step 10 Hz accumulator with a
  spiral-of-death guard; the game drives her lever/bypass controls and
  reads her state for every display. See §4 — this block is untouchable.
- **Rendering.** Canvas world: parallax layers, pre-rendered static
  scenery blitted per frame, baked lighting / shared shading kit,
  code-drawn articulated Fluke (no sprite sheets), camera with dead
  zone, look-ahead, and approach zoom (zoom is a state — in on
  approach, steady while operating, out on leaving; never speed-based).
- **HUD.** Analog dials only, never bars: 7 gauges — TEMP / PRESS /
  POWER / REACT / PERIOD / STEAM / LEVEL — pre-rendered faces,
  spring-damper needles with jitter, zone arcs derived from Samira's
  constants. Three tiers: mini-dial strip, collapsible deck (auto-opens
  on amber/red), focused dial + trend. Pinned live plant diagram
  (true-shape SVG schematic, tap a component → detail card) counts
  inside the HUD budget: total HUD ≈124 px of 844 (≈14.7%).
- **Input.** One unified Pointer Events layer; touch, mouse, keyboard,
  and Xbox gamepad all write a single input-state snapshot the loop
  reads. Hold-to-operate is the core verb (valve 1.5 s, switch 0.8 s,
  reversible, stalls on release — never snaps). Buttons are navigation
  and action only.
- **The Chief.** Guide in a small CRT TV window (jaw-flap while
  speaking, captions always). All speech funnels through the single
  function `chiefSpeak(text, priority)` — the one hook where
  pre-rendered voice clips are looked up by exact line text before
  falling back to Web Speech TTS. Reaction tables, callouts
  (`CALLOUTS`), step explanations (`ASSIST_EXPLAIN`), and demonstration
  lines (`SHOWME_LINES`) are the line sources; see the wiring manifest
  §A0–§A3 before touching any of them. Fluke's lines are **not** the
  Chief's — do not wire Fluke quips through `chiefSpeak` (manifest §A4).
- **Procedures / levels.** L1 operator startup, L2 maintenance rounds,
  L3 control-room / grid dispatch. Numbered procedure steps (R64) drive
  guidance, the demo/takeover driver, and scoring. Demo takes over
  **from the player's current state** (no restart), diagnoses and fixes
  problems by procedure with narration, and hands back on any input.
- **Cinematics.** In-engine achievement/recovery sequences (5–10 s,
  unique per event key, dismissible by any input), plus pre-rendered
  video where wired (`SN_CINE`); teach narration lives inside the
  finished videos, not as standalone wiring (manifest §A5).
- **Audio.** SFX and voice clips are external sibling files
  (`voice/`, `cine/`) in the publish/Android trees — the one exception
  to "everything inlined", by design. Web Audio for synthesized sounds.
- **Performance budgets (hard).** File ≤1.5 MB target / 3 MB max;
  ≤100 draw calls/frame target (150 max); ≥30 fps sustained (60 target,
  30 is a first-class mode); DPR capped at 2; no canvas >2048²; zero
  hot-loop allocations; sim/gauge reads ~10 Hz, text updates only on
  change. Adaptive quality sheds parallax → particles → steam → DPR,
  never gauges, physics, or the diagram.

## 4. INVARIANTS — never break

Breaking any of these is a failed ship, regardless of test results.

1. **Samira's physics block is byte-identical, always.** *(Audit branch
   2026-11-27: patch165 made ONE authorised, recorded deviation — the block
   MD5 on that branch is `be5a0982bf00617bda59847174d69474`; see
   `docs/MODEL-FIDELITY.md` "Audit-branch physics deviation". Ship #24 and
   `main` remain `a3385f4f…` until Kevin confirms or reverts it.)* The `BWR`
   block's MD5 is **`a3385f4f29207be552c4a1c48b620d9b`** (Decision 9:
   "There shouldn't be any deliberate differences" — her constants,
   trips, start state, and behaviour are the source of truth; see
   `docs/MODEL-FIDELITY.md`). Extract and check it exactly this way
   (method from `MODEL-FIDELITY.md` / every patch script):
   ```python
   i = html.index('const BWR = (() => {')
   j = html.index('})();', i)
   assert md5(html[i:j+5].encode()).hexdigest() == 'a3385f4f29207be552c4a1c48b620d9b'
   ```
   Every patch script asserts this **before and after** applying and
   aborts on mismatch. The test suite also extracts and evaluates the
   same slice and asserts her constants/behaviours — if the block is
   not found, the suite exits 1 immediately. Time scaling, game-layer
   clocks, and presentation may change; her numbers may not.
2. **Changes ship as numbered patch scripts against a pinned base MD5 —
   never hand-edit the live game file.** A patch is a Python script
   (`patches/patch<N>[-slug].py`) that: names its base MD5, makes
   anchored exact-count replacements (`assert count == 1` per anchor),
   and asserts invariant 1 before and after. Back up the pre-patch
   file first (`small-nukem.html.bak-pre-patch<N>` or equivalent named
   backup). If your change can't be expressed as such a script, stop.
3. **SFX + voice are MUTED ON LOAD.** Audio starts only after a user
   gesture / explicit unmute; the mute state persists. No sound may
   play on page load, ever.
4. **SHOW is the Chief demo/follow toggle — green = following,
   red = stopped.** SHOW starts/stops the Chief's demonstration/follow
   behaviour. **No press/hold ever summons the Chief** — buttons are
   navigation and action only; there is no offer pop-up and no
   progression gate (both were removed completely; do not re-add them).
5. **30-second cap on every step.** No single step, test, or action —
   passive waits included — may take longer than 30 s of player time.
   Enforced by a suite gate that measures time-to-complete for every
   step in every level; met via the game-layer clock (SPEED control /
   auto-acceleration during passive waits), never by editing physics.
6. **Readings pop-ups only after >3 s dwell.** A readings panel/pop-up
   appears only after the player has stood in front of the panel for
   more than 3 seconds. The rule applies consistently to every
   readings pop-up in the game. No walk-past pop-ups.
7. **One file, safe shutdown, real terms.** The game stays one
   self-contained HTML file; failures end in safe shutdown, never an
   explosion; technical terms are used for real and paired with a
   plain-English explanation, never dumbed down or replaced.

### Run the tests

```bash
python3 check-scripts.py game/small-nukem.html   # node --check over ALL script blocks; expect: 3 blocks, all OK
node tests/value-checks.mjs                      # full suite; prints PASS/FAIL per check, then "<n> passed, <m> failed"; exit 0 iff 0 failed
```

Ship tallies for reference: #17 381/381, #22 443/443 — the count grows
as patches add locks; what matters is **all pass, exit 0**. Also verify
the physics invariant directly (§4, snippet) and record the build
identity: `md5 game/small-nukem.html` (macOS) / `md5sum` (Linux) + byte size.

Gate screenshots/measurements (optional, pre-repo tooling):
`node capture-gates.mjs`, poses via `small-nukem.html?gate=m1|deck|cold|critical|alarm|scram|perf`,
always at 390×844 device emulation.

### Build the APK — Mac

```bash
# 1. MANUAL asset sync — no script/Gradle task exists; skipping this ships the OLD game
cp game/small-nukem.html android/app/src/main/assets/index.html
#    plus any new sibling assets into android/app/src/main/assets/… by hand
#    verify: shasum -a 256 of source and asset copy must match
```

(`signingConfig signingConfigs.debug`) — **do not regenerate the
keystore**, or install-over (`adb install -r`, versionCode stays 1)
breaks. On the Mac, `adb` is not on the SSH PATH: use
`~/Library/Android/sdk/platform-tools/adb`, always with `-s <device>`.

## 6. Ship + release conventions

- **One integrator composes patches.** Workers/streams prepare patch
  scripts + their test locks against a named base MD5; only the single
  integrator applies them, in the ship's stated composition order,
  checking the running MD5 after every patch (each step's output MD5
  is pinned in the ship entry — ship #24's chain is the model).
  Stale-base patches are rebased by the integrator, not force-applied.
- **Patch numbering is global and monotonic.** Game patches
  `patch<N>[-slug].py`, test companions `patch-tests<N>.py`; suffix
  letters (`146b`) are follow-ups within the same ship. Never re-use a
  number, never apply a file marked `.dupagent-do-not-apply`, and
  check for in-code patch tags claiming a number before taking one
  (ship-procedure history: 147 was claimed in-code before any
  `patch147*.py` existed).
- **Suites must pass before anything ships:** `check-scripts.py`
  (3 blocks clean) + `node tests/value-checks.mjs` (all pass) +
  physics-block MD5 re-verified on the final file (§4). New behaviour
  ships with new locks in the same ship; a lock rewritten in place
  (superseded behaviour) is noted as such in the lock text and ship log.
- **Tag `ship-N` per ship** (e.g. `ship-24`) on the exact commit whose
  game file MD5 matches the ship log entry.
- **APK attached to the GitHub Release.** Each ship's GitHub Release
  (named for `ship-N`) carries the release APK built from that ship's
  game file (§5), with the APK's size + MD5 recorded in
  `docs/SHIP-LOG.md` alongside the game MD5, gate tallies, and publish
  verification (build / publish / public URL MD5s).
- **Backups before patches** (§4.2), and the ship log entry names the
  backup, the base MD5, every patch applied in order, deferred items,
  and any expected-update test failures the integrator resolved.

## 7. Glossary

| Term | Meaning |
|---|---|
| **BWRX-300** | GE Vernova Hitachi boiling-water small modular reactor the game models: 870 MWt / 300 MWe. Player-facing naming is just "BWRX-300". |
| **MWt / MWe** | Megawatts thermal (heat the core makes) / megawatts electric (power the generator delivers). 870 MWt → 300 MWe here. |
| **SCRAM** | Emergency shutdown: all control rods drop in by gravity. The protection system trips on her three thresholds only — pressure >8.3 MPa, power >112%, water level <62%. |
| **RPV** | Reactor pressure vessel — the vessel containing the core; its local panel is a walk-to panel in the world. |
| **Fluke Nukem** | The player character — the operator you walk through the plant. His one-liners are his; never wire them as the Chief's voice. |
| **The Chief** | The guide/operator character in the small CRT TV window: briefings, reactions, demonstrations (SHOW), takeover narration. Voice: §9. |
| **dwell** | Standing in front of a panel. Readings pop-ups require **>3 s dwell** (§4.6). |
| **SHOW** | The Chief demo/follow toggle: green = following, red = stopped (§4.4). |
| **ship** | One integrated, gated, published release of the game, numbered (`ship #24`). A ship = composed patches + passing suites + publish + APK + log entry + tag + Release. |
| **patch** | One numbered Python script (`patch<N>.py`) making anchored, exact-count replacements to the game file against a pinned base MD5 (§4.2). The only way the game changes. |

Other terms you'll meet: **reactivity (mK)** — how far the core is from
balance, ×1000 of her Δk/k; **reactor period** — power doubling time
(1 / her smoothed d(ln n)/dt); **isolation condenser (IC)** — passive
gravity cooling, no power needed; **bypass valve** — routes steam to
the condenser to control pressure (the game's steam valve works her
bypass); **annunciator** — back-lit alarm tile on a panel.

## 8. Known pitfalls

- **iOS Safari viewport/chrome compressing the canvas.** Safari's
  collapsing address/tool bars change the visible viewport height, so
  a canvas laid out against a fixed 844 px (or `100vh` naively) gets
  compressed or clipped. Lay out against the *actual* visible viewport
  (`visualViewport` / dynamic viewport units), respect
  `env(safe-area-inset-*)` with `viewport-fit=cover`, and re-measure on
  resize/orientation. Test at 390×844 **and** smaller iPhone viewports
  (e.g. 375×667) and a large one (430×932) — this class of bug shipped
  once as the "iPhone fix" (ship #23) precisely because only the
  reference size was checked.
- **Canvas text scaling at high DPR.** Text drawn on canvas scales
  with `devicePixelRatio` (capped at 2): measure and draw text in the
  same coordinate space, or labels overflow/shrink on retina phones
  while looking fine at DPR 1 on desktop. The ship #24 canvas-text
  work exists because of this — if you touch text rendering, re-check
  at DPR 1, 1.5, and 2, and never trust a desktop-only screenshot.
- **Test-harness synthetic touch limits — bot failures ≠ game defects.**
  Headless/automated drivers cannot reproduce every real touch path
  (multi-touch pointer capture, hold timing, dwell under real finger
  input). A step the harness bot fails is **not** thereby a game
  defect: check whether a human input path exists and works (device
  pass) before patching the game for a bot. Conversely, never loop a
  test step endlessly — after 3 tries, log it and move on; never test
  at 10× speed.
- **Stale everything.** Three stale-copy traps recur: (1) the Android
  asset copy (§2) — rebuild without the manual `cp` ships the old
  game; (2) `publish.sh` copies only the HTML — new assets must be
  placed by hand or the live site 404s them; (3) browser cache serving
  an old build on the live URL — verify MD5 (§5) and the loaded
  build's version on every playtest load.
- **Old line numbers.** The wiring manifest's line numbers predate
  ships #23–#24. Anchor on function/table names and exact strings,
  not line numbers.
- **Fluke ≠ Chief.** Cinematic quip lines (`SN_CINE.DEFS.<key>.line`)
  render through Fluke's speech path even when a same-text clip exists
  in the Chief's voice. Wiring one as Chief is a known, documented
  mistake (manifest §A4) — don't repeat it.
